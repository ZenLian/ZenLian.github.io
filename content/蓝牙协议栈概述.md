## 传统蓝牙与低功耗蓝牙

蓝牙协议栈分为**传统蓝牙**（Bluetooth Classic）和**低功耗**蓝牙（Bluetooth Low Energy，**BLE**）：

- 两者**不兼容**。两种协议在物理层上的定义不同，所以传统蓝牙设备不能与低功耗蓝牙设备进行通信。不过现在很多蓝牙设备都是双模的（比如手机），可以同时与传统蓝牙设备和低功耗蓝牙设备通信，实际上是通过双模蓝牙芯片在两种模式间不断切换实现的。
- 传统蓝牙实际上包括了 Basic Rate（BR）和 Enhanced Data Rate（EDR），又叫 **BR/EDR**。适用于**持续数据**的传输，如音频传输。传输速率大（BR 为 1Mb/s，EDR 最高 3Mb/s），功耗相对高。只支持点对点传输。
- 低功耗蓝牙简称 **BLE**，适用于**间断性数据**的传输，如传感器等。传输速率小（125Kb/s~2Mb/s），功耗低。支持点对点、广播、mesh 传输。
- BLE 是物联网的发展趋势，可扩展性很高，同样能实现传统蓝牙的应用需求。

## 蓝牙协议栈

![[BLE-stack.png]]

需要注意蓝牙协议栈是一个完整的 OSI 协议栈，下到物理层、上到应用层，在蓝牙标准中都作了规范。上图是 BLE 协议栈的示意图。整个协议栈分为 Host 和 Controller 两部分，通过 HCI 连通：

- **Host** 是操作系统，负责上层协议。
- **Controller** 是蓝牙芯片，包括物理层、链路层、同步适配层等。协议细节由芯片实现，应用开发人员不需要关心。
- **HCI** 是 Host 和 Controller 之间的接口。蓝牙标准中规定了 HCI 的通信逻辑，物理上可以由 UART、SDIO 等接口实现。

> [!note]
> Host 和 Controller 在蓝牙从设备（如温度传感器）中一般是集成在一个 SoC 中的，在主设备（如手机）中则是分开的，Controller 是一个单独的蓝牙芯片。

## BLE 协议栈

![[BLE-stack.png]]

BLE 协议栈和 [[传统蓝牙协议栈]] 有很大的区别，首先在 Controller 部分物理信道的定义就不同，所以两种协议栈是无法通信的。在 Host 部分最大的区别在于，BLE 的 Profile 都是基于**属性表（Attribute Table）** 进行通信的，开发人员需要了解以下几层协议：

- [[#ATT]]
- [[#GATT]]
- [[#GAP]]

### ATT

ATT（Attribute Protocol，属性协议）层定义了**属性表**以及针对属性表的**通信协议**，并将通信双方分为**客户端**和**服务端**：

- 由服务端维护**属性表**；
- 客户端根据**通信协议**对服务端的属性表执行查询、设置等操作。

#### 属性表

属性表中的每条属性由以下字段组成：

- **句柄（handle）**：属性的索引值，客户端可以通过句柄来索引该条属性。范围为 0x0001~0xFFFF。
- **UUID**：唯一的 ID 值，表示属性的类型。蓝牙标准中定义了很多常用的 BLE 属性 UUID。
- **值（value）**：属性的值，数据类型可能是字符串、数字、列表等，不同的 UUID 对应值的类型也可能不同。
- **权限（permissions）**：属性的读写等权限。

ATT 层不关心每条属性的具体含义，而是交给上层协议 GATT 去定义。ATT 只是提供了这么一个属性表，以及围绕属性表通信的数据包格式。

#### 通信协议

ATT 基于属性表进行通信，定义了一系列不同类型的数据包（**PDU**s）。

PDU 数据包的格式为：

- opcode：代表 PDU 类型。
- 参数：附带的数据，长度由 opcode 决定。
- 认证签名：用于安全认证，一般不用，因为在链路层可以进行安全认证。

ATT PDU 有以下几种类型：

- **命令**（Commands）由客户端发给服务端，不需要回应。
- **请求与响应**（Requests and Responses）。客户端向服务端发送请求，服务端发送响应。30s 内未响应算作超时。
- **通知**（Notifications）。由服务端发给客户端，不需要回应。
- **指示与确认**（Indications and Confirmations）。服务端发送指示给客户端，需要客户端发送确认回应。

### GATT

GATT（Generic Attribute Profile，通用属性配置文件）是对 ATT 层的进一步封装，同样把通信双方分为**服务端**和**客户端**。应用层 Profile 几乎都是基于 GATT 的。

#### 服务、特征和描述符

GATT 将 ATT 中的属性重新划分为 3 种类型，定义成更高级别的数据结构**服务（services）**、**特征（characteristics）**、**描述符（descriptors）**。这三者是包含关系，如下图：

![[GATT_Service.png]]

**服务**代表了设备的能力，可能包含一系列**特征**；特征又可能包含一些**描述符**。

标准的服务、特征和描述符都会定义在 BLE 手册里，如设备信息、电量信息等服务，并分配一个独有的 UUID。厂家也可以定义自己的属性，并定义自己的 UUID。

下图是 GATT 的属性表定义示例，包含了标准属性和自定义属性。

![[GATT_Attributes.png]]

#### 流程

GATT 标准中还定义了一系列涉及以上数据类型的操作流程，应用层可以通过 API 执行这些流程。包括服务发现、特征发现、描述符发现、读写特征值、特征值通知等。这些 GATT 流程底层使用的是 ATT 层的 PDU 通信流程。

### GAP

GAP（Generic Access Profile，通用访问配置文件）定义了设备发现和连接等流程，是所有蓝牙设备必须实现的 Profile。

广播和扫描是 GAP 的核心内容，实际上这些广播包和扫描包都是定义在链路层的，GAP 定义的是如何使用这些数据包进行设备发现、建立连接等流程。

#### 角色

GAP 将参与通信的设备分为 4 种角色（Roles）：

- **广播者**（Broadcaster）：向外发送无连接的广播包。
- **观察者**（Observer）：接收广播包。
- **外围设备**（Peripheral）：被动接受中心设备的连接。
- **中心设备**（Central）：主动发起与外围设备的连接。

> [!note]
> 这 4 种角色与 GATT 中的客户端和服务端没有对应关系，任何一个角色都可以同时作为客户端和服务端。

#### 设备发现流程

外围设备想要被中心设备发现时，会发送广播包广播自身的信息。此时外设同时作为广播者。发送广播包时，外围设备必定处于以下几种模式之一：

- **可发现**（discoverable）模式：可以被中心设备扫描到。
- **不可发现**（non-discoverable）模式：这些广播包会被中心设备的设备发现流程所忽略。

中心设备想扫描外设时，进入扫描模式，作为观察者接收广播包。GAP 定义了两种扫描模式：

- **被动扫描**（passive scanning）：只接收广播包，不发送扫描包；
- **主动扫描**（active scanning）：接收到广播包之后，会发送扫描包进一步查询外设的信息。

#### 设备连接流程

外设广播包中带有一个**可连接标识**，告诉中心设备它是否可以被连接。中心设备可以向可连接的外设发起连接。
